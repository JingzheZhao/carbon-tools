# 第一部分：产品与方法论

## 一、产品定位

| 项 | 决定 |
|---|---|
| 性质 | **开源、免费、非商业**工具 |
| 专业范围 | 景观设计 + 城市设计为主，不涉及细部构造 |
| 设计阶段 | 概念 / 早期设计阶段 |
| 对标产品 | Carbon Conscience (Sasaki)、Pathfinder (Climate Positive Design) |

**差异化定位**：

1. **在 Rhino 里实时计算** —— 设计师本来就在 Rhino 里推方案，不需要另外画一遍。CC 要求用户在网页上画多边形，"很难用也不准"
2. **三维 + 可视化表现力** —— CC 偏 2D 和表格
3. **AI 建议 + 方案对比**
4. **更少的提问，不牺牲精度**（2026-08-28 修订，原为"更粗的颗粒度"）—— CC 的 230+ 个类型是「材料族 × 挡墙密度 × 人行/车行 × 气候区」乘出来的，后三个轴根本不该问用户。几何与项目地点自动消解其中 44%（193 条景观配方中的 85 条）。原来的"更粗的颗粒度"是拿精度换易用性，这条不成立也不必要 —— 两样可以同时拿到。详见系统设计文档 §四「来路」。

## 三、计算框架

概念阶段的碳账本 = 五笔账，按年份排到时间轴上累加，得到**累计净碳曲线**，穿过零线那年 = 碳中和年。

| # | 科目 | 发生时点 | CC 是否含 |
|---|---|---|---|
| ① | 材料生产 A1-A3 + 运输 A4 + 施工 A5 | 第 0 年 | ✅ 全含 |
| ② | 现状损失（砍树、土壤扰动） | 第 0 年 | ✅ 含（拆除与场地准备类） |
| ③ | 维护 B2-B3（年度） | 周期性 | ❌ **不含** |
| ③ | 更换 B5（按寿命脉冲） | 周期性 | ✅ 含 |
| ④ | 植物固碳 + 土壤固碳（非线性） | 每年 | ✅ 含（归入 D） |
| ⑤ | 期末处置 C | 期末 | ❌ **不含** |

**研究周期：60 年**（跟随 CC V2；CC V1 曾用 80 年）
理由：CC 的固碳数值就是投影到第 60 年算出的，用他们的数据必须对齐。60 年也是 Tally / Athena / EPIC 的 WBLCA 标准时间线。
（注：CC 附录引用 ILFI 达标线时用 50 年 —— <500 kgCO₂e/m²/50yr；Atelier Ten 建议 185 kgCO₂e/m²/50yr。报告里若引这些基准需注明周期差异。）

**我们相对 CC 的方法论增量**：

- **维护碳（B2-B3）—— 一期不做（2026-08-28 已定），但理由要换。**
  原先的理由是"CC 结论章讲了低维护标准的问题却没算进模型，这是缺口"。缺口确实存在，但数据核查后发现更要命的一点：**搜遍 259 条构件，维护/运营碳一条都没有**（命中的 10 条全是灌溉**硬件**的 A1-A3 生产碳 —— 管道、喷头、控制器、气象站、水泵，没有一滴水、一次修剪）。
  所以做维护碳 = **离开 CC 数据集**，要自己建因子、自己找文献、自己扛争议 —— 这恰好推翻了 §二 "用 CC 数据省 3–5 人年"的核心逻辑。
  **处理方式**：一期不算；把灌溉硬件（数据里有）单独显示当钩子；报告里明写"与 CC 一致，不含 B2–B3 运营碳"；列为二期独立模块，有自己的文献支撑。这样方法论边界干净，不会让一个模块拖垮整个数据策略的合法性。
- **C 阶段** —— CC 不算，理由是概念阶段处置方式太不确定。这个理由较充分，优先级低。

## 四、CC 的固碳模型（可直接采用）

**逻辑斯蒂（S 型）曲线**：

```
Ct = M / (1 + e^(−r × (t − M/2)))

Ct = 第 t 年的累计固碳量
M  = 碳承载力 = 成熟系统总储碳（TCP）
r  = 分布式固碳率，拟合到成熟年份：
     木本生态系统 80 年（USFS 2003）
     草地 20 年（Deng et al., 2022）
湿地例外 —— 用线性回归，不用逻辑斯蒂
```

**扣除分解后的真实固碳率**：

```
TSR = ASR − ((ASR × LPG) × DF)

ASR = 文献中的年均固碳率
LPG = 叶片占生长量的比例（易分解部分）
DF  = 分解因子（按气候带）
```

**总储碳潜力**：`TCP = 地上生物量 + 地下生物量 + 土壤有机碳`
**换算**：`GWP = 碳质量 × 3.66`

**关键经验参数**：

| 参数 | 数值 |
|---|---|
| 干生物量含碳率 | 50% |
| 地下生物量乘数 — 森林 | 20% |
| 地下生物量乘数 — 草原 prairie | 300% |
| 地下生物量乘数 — 干草甸 | 200% |
| 地下生物量乘数 — 草地/湿地 | 12.5% |
| 城市土壤有机碳 | 2.8 × 生物量 |
| 分解 1 年后剩余 — 暖气候 | 24% |
| 分解 1 年后剩余 — 冷气候 | 60% |
| 分解 1 年后剩余 — 湿地 | 70% |
| 草坪当年生长进入 SOC 的比例 | 5% |
| 异源碳（allochthonous） | 年固碳率的 5%（仅湿润森林，仅 80 年后，之后线性） |
| A5 安装余量 | 低 1% / 平均 3% / 高 4% |

**重要结论**：土壤储碳常常等于或超过生物量储碳，只算活体生物量会遗漏大半。

## 五、植物计量方式（2026-08-28 已定：做单株）

**决定：做，而且很便宜。** 面积 + 单株乔木。

**原先的顾虑不成立。** 之前记的是"CC 是**有意**选择按土地面积而非茎密度计量的（Braakhekke et al., 2019）"，因此担心做单株等于挑战 CC 的方法论。拿到数据后发现：**CC 的城市树固碳本身就是按株距参数化的**，只是被冻结成了三个点：

| 树冠覆盖 | 株距 | ㎡/株 | 固碳 kgCO₂e/㎡ | 反解：每株 |
|---|---:|---:|---:|---:|
| 17% | 12 m | 144 | −2.66 | −383 |
| 35% | 6 m | 36 | −5.63 | −203 |
| 50% | 4 m | 16 | −8.51 | −136 |

（构件 `329300.28 / .29 / .30`，名称里直接写着 "trees 12M o.c." / "6M o.c." / "4M o.c."）

街道树配方里的构件名更直白：`5 cm Cal. B&B/Box Tree Planting (1 Tree/10 SM)` —— **每 10㎡ 一棵，写死的**。

所以这不是"要不要挑战 CC"的问题，而是 **CC 已经算了株数，只是把它冻结成了常数**。反解回去即可，三点插值，工作量极小。Rhino 里树本来就是点或块，棵数、位置、间距全都现成。

> ⚠️ **关键细节**：每株固碳随密度**下降**（竞争）。绝不能写成 `N × 常数`，必须沿这条曲线插值。
> 这也是对甲方讲故事的素材："多种一倍的树，固碳不到一倍。"

**乔木分组（若做更细的规格区分）**：按成熟冠幅 3 组（小 <6m / 中 6-12m / 大 >12m），生长速度作二级参数默认中速（给 AI 留接口），气候区系数自动推导，必须内建存活率。

## 六、场地现状（第②笔账）

**必填，但默认只需一次点击。**

这往往是项目里最大的一笔账，且是设计真正能改变的部分。核心叙事："保留这排树 = 少铺 400㎡ 混凝土"。

**CC 的处理方式**（可直接沿用）：

- 假设有机碳在拆除与场地准备中**全部释放**
- 全局假设：平均 0.5 米深度整平、清理除根、场地保护
- 废弃物默认运往 16 km 内的设施（距离与运输方式用户可编辑）
- 储存碳记为负值，拆除时按等量正值释放（例：温带森林 −79.77 CO₂eKg/m² 储存 → 拆除释放 +79.77）
- 原地打捞回用：加破碎机碳成本，减去等体积进口骨料的开采加工运输成本 → 净节省

**机会成本**（这些树本会继续固碳）→ **不计入主数字**，改为画一条"什么都不做"的基准曲线并排对比。

> 双曲线图预计是产品最有传播力的一张图：两线之间的面积 = 这个设计的真实代价或贡献。
> 天然回答甲方那句"那我不做不就行了？"

3. **A/B 方案对比** —— 怎么走过去

*不做*"相当于 X 辆车"这类等价物换算。

**CC 附录 D 的部分参考值（kgCO₂e/m²，读图近似）**：现浇人行混凝土 ~190、砖铺沙基 ~205、整石沙基 ~130、稳定砾石 ~68、沥青人行 ~68、现浇混凝土墙 ~1205、干砌石墙 ~450、木墙 ~5、EPDM 安全地垫 ~322、覆盖物安全地垫 ~22。修复类（负值）：红树林 −265、温带海洋性雨林 −143、温带湿地/盐沼 −92、热带雨林 −87、北方林 −85、温带大陆林 −75、草原 −58。

## 八、不确定度呈现

**主显中位值，副显区间**（大字一个数，下面小字区间；图表用误差带）。

关键定义：**区间代表的不是"数据误差"，而是"设计选择空间"**。

- 区间下端 = 这套方案如果全部选低碳做法能达到的水平
- 区间上端 = 全部按常规做法的水平
- 中位值 = 行业典型做法

这样区间从一个"我们也说不准"的免责声明，变成一个**可执行的目标**——"你现在在 520，但同样的设计做到 380 是可能的"。也天然衔接 AI 建议。

**CC 的做法可对齐**：材料碳因子存 LCf / MCf / HCf 三档（引用数 >5 时 MCf 为真中位数，上下为标准差；引用少时为简单平均与最低/最高值）。注意：**生态碳只有单一值，无三档**。

## 九、分类体系

**底层数据结构 = 按设计元素组合（可替换槽位）；界面不做场景包装，改由「来路」机制解算。**（2026-08-28 修订，原为"界面一期用功能场景入口包装"，理由见本节末）

CC 的三层结构（可直接沿用）：**基础材料 → 场地要素 element → 每种土地利用的平均组成**

```
广场 500㎡
├─ 铺装：混凝土现浇          [可换]
├─ 基层：150mm 碎石垫层      [可换]
├─ 树池：8 个                [可改]
└─ 座椅：12m                 [可改]
```

关键理由：**只有"可替换的槽位"存在，AI 建议功能才成立**。纯场景黑盒里没有槽位可换，AI 只能说空话。

**CC 的景观四大类**：Existing to Remain / Demolition & Site Preparation / Hardscape（11 子类）/ Softscape（4 子类）

**CC 的硬景命名逻辑**（很值得学）：先由铺装类型定义，再由**墙体密度**区分 —— 1% 墙 = 简单开放广场、5% 墙 = 有高差和种植池的复杂广场、10% 墙 = 高度复杂空间。规划阶段默认取 5%。

### 我们的方案（2026-08-28 重定，原为"20 个场景入口"）

> **「20 个场景入口」取消。**

原计划：在 230+ 个土地利用之上做一层 20 个左右的场景入口，盖住 80% 的情况。

**拿到数据后发现这是治标。** 230 个类型不是分类问题，是**"看不见几何"的问题** —— CC 只能把几何问题伪装成选择题抛给用户。它的列表是这样乘出来的：

```
材料族 × 挡墙密度 × 人行/车行 × 气候区
```

后三个轴根本不用问用户：

| 轴 | CC 怎么办 | 我们怎么办 | 占 193 条 |
|---|---|---|---|
| 气候区 | 每个生态系统复制 N 份 | 项目地点定，设一次 | 48 条 (25%) |
| 挡墙密度 1%/5%/10% | **让用户猜** | 竖直面积 ÷ 平面面积，Rhino 直接量 | 26 条 (13%) |
| 墙/台阶/栏杆 | 拆成独立 landuse | 面法线方向自动识别 | 11 条 (6%) |
| **材料族** | 用户选 | **用户选（唯一真正的设计决策）** | 108 条 (56%) |

挡墙密度那个下拉框的代价（同一块 1000㎡ 广场，实测）：

| CC 选项 | 隐含挡墙 | 中位 tCO₂e |
|---|---:|---:|
| minimal walls (1% or less) | 10 lm | 173.9 |
| some walls (5%) | 50 lm | 286.8 |
| significant walls (10%) | 100 lm | 446.1 |

**一个下拉框 2.6 倍、272 吨的摆动，全靠用户瞎猜**，而它是纯几何量。

**新方案 —— 来路机制（Provenance）**：不包装 CC 的列表，把它拆开。每个子构件打三类标签之一：

| 来路 | 数量从哪来 | 用户能做什么 |
|---|---|---|
| **实测** | Rhino 几何直接量 | 改模型 |
| **推定** | 实测值 + 一条明写的规则 | 改规则（很少需要） |
| **假设** | CC 配方默认值 | 改数值，或去模型里画出来 |

**关键性质：优雅降级。** 用户什么都不画只给平面边界，系统退回成 CC 的答案一分不差（已验证：量到 10 米墙时算出 131.0/173.9/240.6，与 CC 1% 档逐位吻合）。每多画一样东西，就有一个「假设」被「实测」替换。

**AI 的槽位不用另外设计** —— 来路标签就是槽位，AI 只在「假设」上动手。

用户从头到尾**不选场景**，只选材料族（= 颜色，见 §十三）。完整论证见 `Carbon工具-系统设计.md`。

> **注**：目录式入口本身没错，错在用错了轴。**材料轴不做，问题轴要做** —— "这个方案能不能达到 2030 目标"、"保留这排树值不值"这类 workflow 目录是对的。见 `Carbon工具-UI交互设计.md` §十三。

## 十、评分体系

**暂缓，二期再说。** LEED / SITES 里能从碳模型自动推导的条款很少，大部分是文档、流程、场地条件类。若做，定位为"预评估 / 自查清单"，非官方计算器（商标合规）。

（注：CC 参考文献里有 USGBC 2021 *SITES Pilot Credit 3: Assess and Improve Site Carbon Performance* —— 后期做评分时的直接入口。）

## 十一、CC 自己承认的研究空白（我们的机会）

- **景观项目的 A5 施工碳** —— 他们明确说"找不到任何相关研究"
- **苗圃隐含碳** —— 文献中"最大的单一空白"，无 EPD 标准
- **城市景观/花园固碳** —— 研究者少，且集中在美欧
- **维护/运营碳** —— 明确排除，但他们自己在结论里承认这是制度性障碍
- 照明、电气、灌溉、水景、电信产品用 **Product Placeholders** 占位，部分无一手引用

# 第二部分：技术架构

## 十二、核心分工原则

> **GH 只管几何和量，网页管所有语义。**

这条原则推导出后面几乎所有的技术决定。

## 十三、Rhino 端怎么标记（已定：颜色分组）

**决定：用户在 GH 电池上选一个颜色，把几何塞进去。颜色就是分组键。**

否决的方案与理由：

| 方案 | 否决理由 |
|---|---|
| 按图层自动识别（要求固定命名） | 强制用户改建模习惯，插件死亡率最高的地方 |
| 读取现有图层 + 网页映射表 | 每个公司图层标准不同；概念阶段图层往往很乱甚至没有 |
| GH 电池里放材料下拉 | CC 有 230+ 类型，GH 的 value list 超过二三十项就不能用了；且材料库更新要重发插件 |

**颜色方案的三个好处**：

1. **插件与数据库解耦** —— 材料库活在网页端，可在线更新，GH 插件永远不用重发。对开源项目是维护成本上的巨大差别
2. **所见即所得** —— 颜色同时是 Rhino 视口显示色，分组过程本身就产出一张彩色分区图，那本来就是景观和城市设计的通用语言
3. **颜色贯穿全产品** —— Rhino 视口 → 网页三维 → 图例 → 饼图柱状图 → 报告，用同一套色。视觉语言由用户自己定义，不需要另外设计

**已知风险**：用户在 GH 里调了色，映射就断（key 是 RGB）。解决在网页端——记住"红色 = 现浇混凝土"，发现红色消失、出现新的深红时提示"是这个吗？"，一键继承。不增加 GH 端输入。

## 十四、电池设计

```
┌─────────────────────┐        ┌─────────────────────┐
│ CC Group            │        │ CC Sync             │
│  ▸ Geometry         │───┐    │  ▸ Objects  (+可加口) │
│  ▸ Color ■          │   ├───▸│  ▸ Run      (toggle) │
│  ◂ Tagged Objects   │   │    │  ▸ Open     (button) │
└─────────────────────┘   │    │  ◂ Status / Port    │
        (可复制多个)  ─────┘    └─────────────────────┘
```

**Sync 的开关要拆成两个**：Toggle 变 true 后每次重算都会跑，"持续同步"靠它实现；但"弹出浏览器"不能每次重算都执行（用户拖个点就开十个标签页）。所以 `Run`（toggle，同步开关）+ `Open`（button，手动开浏览器）分开。

**项目级参数不进 GH**（项目名、地点、气候区、运输距离假设），放网页上填。GH 端保持干净。

## 十五、协议约定

```json
{ "meta": { "units", "origin_offset", "timestamp", "mesh_tolerance" },
  "groups": [
    { "color": "#RRGGBB",
      "objects": [
        { "id": "几何 hash",
          "quantity": {
            "area": 0,            // 水平投影面积
            "vertical_area": 0,   // 2026-08-28 新增
            "mean_height": 0,     // 2026-08-28 新增
            "count": 0, "length": 0, "volume": 0
          },
          "mesh": { "vertices": [...], "faces": [...] } }
      ] } ] }
```

**五个关键约定**：

1. **所有量纲全部算出来一起发** —— GH 不知道材料类型，所以面积、数量、长度、体积都算，网页拿到类型后取需要的那个。多传几个数字开销可忽略，换来 GH 端完全不需要任何材料知识
   > 数据集实测印证了这条：259 条构件恰好有**四种单位** —— 面积 219 条 / 计数 EA 15 条 / 长度 LM 13 条 / 墙占地 12 条（高度内建于构件，1M 与 2M 两档）。
1b. **竖直面积与平均高度必须单独发**（2026-08-28 新增）—— 这是消解挡墙密度那一轴的钥匙，见 §九。按面法线 Z 分量拆分，阈值 60°：`|normal.Z| > cos(60°)` → 水平，否则竖直。
2. **id 用几何 hash** —— 几何不变 id 就不变，这是增量更新（只推变化的物体）的基础。不能用序号，否则删一个物体后面全错位
3. **单位在 GH 端统一转米** —— Rhino 可能是英尺/毫米/英寸
4. **必须有 origin_offset** —— 景观模型常带真实地理坐标，坐标动辄几十万。three.js 用 float32 那个量级会抖动甚至撕裂。GH 端整体平移到原点，偏移量单独存在 meta 里
5. **坐标保持 Rhino 的 Z-up**，由网页端转成 three.js 的 Y-up

## 十六、几何同步方案（已定：自研）

**自研 GH 组件内嵌本地服务，不用 Speckle。**

否决 Speckle 的理由：用户要注册账号 + 装连接器 + 理解 stream/commit 概念，三道门槛，每道都掉人；而且它的 viewer 样式和交互不由你控制——把最核心的差异化（酷炫可视化）交给第三方不划算。

**推进顺序**（重要，别一上来就啃 WebSocket）：

1. 先定协议
2. GH 端组件写出来，输出 JSON
3. 网页骨架：three.js 读 JSON，做三维显示 + 按颜色着色 + 侧栏列表
4. 传输层从"写文件"换成 WebSocket（协议没变，网页只改数据源那一个函数）

## 十七、后端架构

### 2026-08-30 重定：一期不做后端

原方案（下方保留）是「几何留本地 + 方案快照上云 + 账号」。**现改为一期完全不做后端。**

重新审视「哪些功能真的需要服务器」后发现，需要后端的只有三项，且都不是「没有就不能用」：

| 功能 | 是否需要后端 |
|---|---|
| 门户页、插件下载、文档 | 静态托管即可（GitHub Pages） |
| Rhino → 网页同步 | 否，localhost 更快且离线 |
| 碳与造价计算 | 否，200 KB 数据集在浏览器里算绰绰有余 |
| 用户改默认数据 | 本地覆盖不需要；社区共享才需要 |
| 保存方案 | 单机不需要；跨设备才需要 |
| 账号 | 需要 |

**改判的三个理由：**

1. **客户保密** —— 原方案已经把几何留在本地，但方案快照仍会上传。对一个个人维护、无安全预算的免费项目，替事务所保管任何项目数据都是负债。「所有东西都不离开你的电脑」比「只有几何不离开」更容易通过事务所 IT 审查，也更容易讲清楚。
2. **维护成本** —— 服务器续费、备份、鉴权、密钥、GDPR 永不停止。这是一人维护的免费项目最常见的死因。本地版零成本，且作者停止维护后仍能运行。
3. **NC 许可证** —— CC BY-NC 4.0 下本就不能商业化，所以不存在「为将来收费先建后端」的理由；真要收费得先换数据层，不是加付费墙的事。

**共享材料库改为不用后端实现**：数据集作为带版本号的 JSON 放在仓库里，插件只读拉取，他人通过 Pull Request 贡献。审核环节在这里是优点——碳排因子出错会静默污染别人的报告，不该允许任何人直接写入。

**方案保存**：一期用浏览器 localStorage（已实现，见 viewer.html 的 SCHEMES）。
⚠️ 已知问题：`CarbonSyncServer.FindFreePort()` 每次启动端口都变，而 localStorage 按「域名+端口」隔离，因此**跨 Rhino 会话方案会读不到**。修法是 `FindFreePort()` 优先尝试固定端口，占用再退回随机。待办。

**何时重新考虑**：需要团队协作功能时，或想商业化时（后者需先换数据层）。

### 原方案（2026-08-28，已被上文取代，保留备查）

用户要的是：账号、存历史方案、方案对比。但**不需要一个重后端**。

```
几何（大、敏感、对比时不需要）        →  只在本地，从不上传
方案快照（映射 + 量 + 碳结果 + 缩略图）→  上云，几十 KB
材料库（只读公共数据）                →  静态 JSON，不进数据库
```

三个好处：

- **隐私** —— 很多事务所禁止把模型传到第三方服务器。"我们从不上传你的模型"是很有力的一句话
- **成本** —— 每个方案快照几十 KB，免费档数据库能装几千用户。服务器账单长期接近于零，而不是随用户线性增长
- **离线可用** —— 不登录也能完整使用（建模、算碳、看图表、导报告）。登录只是多了"存下来、以后对比"。第一次用不需要注册，对开源工具传播很重要

**代价**：重开半年前的旧方案看不到三维，只有数据、图表和缩略图。可接受——方案对比看的本来就是数字，真要看三维就重新同步一次，模型在用户自己电脑上。

**颜色→材料的映射存在方案快照里**，跟着项目走，换电脑也在。不需要写回 Rhino，也不需要旁边的 json。

**后端要设计成可自建、可替换** —— 事务所能内网部署，公共实例挂了或作者不维护了别人还能用。

## 十八、开发环境

**.gha 的编译必须在本地做。** Cowork 云端容器和设备上的 Linux 沙箱都连不到 NuGet，拿不到 Grasshopper SDK 包。本地跑 Claude Code 时用的是自己机器的 dotnet 和网络，能编译、能直接丢进 Grasshopper Libraries 测试，闭环最短。

**分工**：需要编译的活（.gha）在本地 Claude Code；方法论、数据分析、白皮书拆解这类在 Cowork。

## 十八·五、代码协作模式（已定）

**Claude 负责写代码，但写完必须带用户走完两步，不能代写完就算完。**

背景：项目全程由 Claude 写代码、执行，用户基本不碰 IDE。担心两件事——一是这样做出来的东西自己不理解、debug 不了；二是面试时会露怯。讨论后结论是：**不需要用户自己手写每一行**，但用户必须达到"会读、会判断"的层级——看到代码要能判断对错、看出边界会不会崩，而不是黑盒使用。

**流程约定**：

1. Claude 写代码（照常，用户不需要打开 IDE）
2. 交付后，Claude 主动带用户过一遍关键的**"如果改动/删除某处会怎样"**边界情况问答（例如：这个 id 用几何 hash，如果两个物体 hash 碰撞了会怎样？origin_offset 不做会怎样？）
3. 让用户**反过来把代码逻辑复述给 Claude 听**，Claude 挑错、验证用户是否真的理解，而不是记住了结论

**验收标准**：用户对每一处写进决策记录的技术理由，要能讲清楚"不这样做会具体坏在哪"，而不只是记住"要这样做"。

**适用范围**：本项目所有代码协作，尤其是文档里明确写了"为什么"的关键决策点（GH 分组逻辑、协议 JSON 结构、几何 hash 生成方式等）；常规样板代码可以适度从简。

**时机调整（2026-08-27）**：逐个电池写完就立刻做完整边界问答+复述，打断了做完整个项目的节奏。改为：**先把整个项目做完，之后做一次彻底的整体复盘**，届时再按上面的流程走一遍所有关键决策点。开发过程中的讲解保持简短（讲清楚"这段代码干什么"就行），不用每写完一块就停下来做完整的问答+复述那一套。

**讲解语言**：用户以后要用英文面试，代码讲解统一用英文（其余项目日常交流不受此限制）。用户完全没有编程基础,直接、完整地讲清楚,不要用开放式问题让用户瞎猜。
