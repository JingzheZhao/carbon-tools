## 零、一句话主张

> **凡是模型量得到的,一律不问用户;量不到的,明确标成假设。**

这条规则推导出后面全部的架构决定。

# 第一部分:问题诊断

## 一、我们真正在解决的问题

不是"CC 有 230 个类型太多了"。是:

> **CC 看不见几何,所以只能把几何问题伪装成选择题抛给用户。**

CC 的混凝土广场分三档,让用户选:

- `minimal walls (1% or less)`
- `some walls (5%)`
- `significant walls (10%)`

把这个问题诚实地翻译一遍,它其实在问:

> "你这块 1000㎡ 的广场上,有 **10 米**、**50 米** 还是 **100 米** 的 1 米高挡土墙?"

概念阶段没有设计师数过挡墙长度,所以用户只能猜。但 Rhino 里那些墙就摆在那儿,精确到毫米。

## 二、猜错的代价(实测)

同一块 1000㎡ 广场,只因这一个下拉框 —— 单位 tCO₂e:

| CC 选项 | 隐含挡墙 | 低 | 中位 | 高 |
|---|---:|---:|---:|---:|
| minimal walls (1% or less) | 10 lm | 131.0 | 173.9 | 240.6 |
| some walls (5%) | 50 lm | 215.6 | 286.8 | 394.3 |
| significant walls (10%) | 100 lm | 334.4 | 446.1 | 610.1 |

**一个下拉框,2.6 倍 / 272 tCO₂e 的摆动幅度,全靠用户瞎猜。**

这个规律不是个例。控制变量对比(同一铺装族,只改挡墙密度),倍数极其稳定:

| 铺装族 | 1% 墙 | 5% 墙 | 10% 墙 | 倍数 |
|---|---:|---:|---:|---:|
| CIP 车行混凝土 | 227 | 337 | 491 | 2.2× |
| 黏土砖(砂基) | 199 | 306 | 463 | 2.3× |
| 整石(砂基) | 119 | 198 | 315 | 2.6× |
| 预制 / CMU 混凝土 | 285 | 374 | 542 | 1.9× |
| 石材饰面(砂浆座浆) | 236 | 340 | 496 | 2.1× |

## 三、关键发现:那个下拉框远不止管挡墙

逐条 diff 三份配方后发现,它同时挪动了 **25 个子构件里的 21 个**:

| 子构件 | 1% | 5% | 10% | 为什么会动 |
|---|---:|---:|---:|---|
| 1M 现浇挡土墙 `033001.04` | 1% | 5% | 10% | 墙本身 |
| 100mm 现浇铺装 `033001.01` | 95% | 90% | 83% | **墙占掉了铺装的地** |
| 150mm 碎石垫层 `321100.01` | 95% | 90% | 83% | 跟着铺装走 |
| 灯杆/灯具/基础 `265600.*` | 0.5% | 1% | 2% | 复杂场地灯更多 |
| 不锈钢排水结构 `334000.01` | 1% | 1% | 3% | 高差多则排水多 |
| 栏杆油漆/金属/木 `099001, 323300` | 1% | 2% | 4% | 有墙就有栏杆 |

**结论**:它不是"挡墙密度",是一个打包好的**场地复杂度档位**。

而这 21 个联动的构件,**可知性完全不同** —— 墙和铺装 Rhino 量得到,灯和排水沟量不到。混在一个下拉框里是 CC 的妥协,不该是我们的。

这一条直接决定了系统的核心抽象。

# 第二部分:核心抽象

## 四、每个数字都带一个「来路」(Provenance)

系统里没有任何一个碳数字是裸的。每一个都必须回答:**你是量出来的,还是推出来的,还是假设的?**

| 来路 | 数量从哪来 | 例子 | 用户能做什么 |
|---|---|---|---|
| **实测** MEASURED | Rhino 几何直接量 | 铺装面积、挡墙面积与高度、木平台面积、树的棵数与位置 | 改模型 |
| **推定** INFERRED | 实测值 + 一条明写的规则 | 铺装面积 = 平面面积 − 墙占地;气候区 = 项目地点;垫层面积 = 铺装面积 | 改规则(很少需要) |
| **假设** ASSUMED | CC 配方默认值 | 配筋率、灯具密度、排水结构比例、油漆道数 | 改数值,或去模型里把它画出来 |

## 五、这个抽象带来的四个性质

### ① 优雅降级 —— 已验证

用户什么都不画,只给一个平面边界,系统退回成 CC 的答案,一分不差。每多画一样东西,就有一个「假设」被「实测」替换掉。

原型验证结果(1000㎡ 广场,tCO₂e):

| 模型里量到的挡墙 | 低 | 中位 | 高 | 对照 |
|---|---:|---:|---:|---|
| 0 米(纯平铺) | 113.0 | 150.1 | 207.9 | CC 无此档 |
| **10 米** | **131.0** | **173.9** | **240.6** | **= CC 1% 完全吻合** |
| 30 米 ← 真实场地 | 167.0 | 221.5 | 306.2 | CC 只能给 174 或 287 |
| 50 米 | 203.1 | 269.1 | 371.7 | CC 5% = 286.8 |
| 100 米 | 293.1 | 388.0 | 535.5 | CC 10% = 446.1 |

**10 米那一行逐位吻合 CC。**这证明我们不是另起炉灶,而是把 CC 的模型解冻 —— 它原本被钉死在三个点上,现在连成了连续的。

原型代码:`tools/resolver_prototype.py`,可直接运行。

> **诚实的边界**:50 米和 100 米两行低于 CC,是因为 CC 的高档位还同时调高了照明和排水,而我们只替换了实测得到的墙与铺装。**这是对的做法** —— 灯和排水沟属于「假设」类,不该被挡墙长度悄悄带着跑。但必须在界面上写明:这两项仍是假设值。

### ② AI 的着力点被自动定义

AI **只在「假设」槽位上动手**。实测值是事实,不该被建议改动;假设值才是"你可以换一个做法"的地方。

这顺带解决了决策记录 §九 里"必须有可替换槽位,AI 建议才成立"那一条 —— **槽位不用另外设计,来路标签就是槽位。**

### ③ 精度是可见的、可积累的

用户能看到"我多画一样东西,精度提高了多少",而不是面对一个黑盒。

### ④ 报告可以自证

每个数字都能追溯到"你画的 30 米挡墙"或"CC 默认假设的灯具密度",这是任何竞品做不到的可信度。

# 第三部分:七层架构

数据从上往下流。每一层只做一件事,并且只跟相邻层说话 —— 这样 GH 插件永远不用因为材料库更新而重发。

## L0 — 数据层(静态只读 JSON,不进数据库)

**内容**

| 文件 | 条数 | 内容 |
|---|---:|---|
| `cc_site_elements.json` | 259 | 基础构件碳因子(低/中/高三档 + 固碳 + 储碳) |
| `cc_landuse_surface.json` | 193 | 景观配方(含完整 subItems 百分比) |
| `cc_landuse_building.json` | 216 | 建筑基准(地上/地下分开) |

**完整性已验证**:配方引用的 214 个构件 id 全部命中,零悬空引用。

**构件的四种单位**(决定了 L2 协议为什么要全量纲一起发):

| 单位 | 条数 |
|---|---:|
| 面积 m² | 219 |
| 计数 EA | 15 |
| 长度 LM | 13 |
| 墙占地 m²(高度已内建于构件,1M / 2M 两档) | 12 |

**唯一的新增工作**:给配方里每个子构件打上「实测/推定/假设」标签。约 25 个类别,一次性人工完成。

**出 →** 带来路标签的构件表

## L1 — Rhino / Grasshopper(只量,不判断)

**电池**

```
┌─────────────────────┐        ┌─────────────────────┐
│ CC Group            │        │ CC Sync             │
│  ▸ Geometry         │───┐    │  ▸ Objects  (+可加口)│
│  ▸ Color ■          │   ├───▸│  ▸ Run      (toggle)│
│  ◂ Tagged Objects   │   │    │  ▸ Open     (button)│
└─────────────────────┘   │    │  ◂ Status / Port    │
        (可复制多个)  ─────┘    └─────────────────────┘
```

**每个物体要量出**:

- 水平投影面积(plan area)
- **竖直面面积 + 平均高度** ← 新增,整个方案的钥匙
- 长度 / 个数 / 体积
- 包围盒、网格

**竖直/水平怎么分**:按面法线 Z 分量分,阈值 60°。`|normal.Z| > cos(60°)` → 水平,否则竖直。

GH 端不需要知道任何材料知识。

**出 →** 每个颜色组的全套量纲

## L2 — 协议

在决策记录 §十五 基础上扩展:

```json
{ "meta": { "units", "origin_offset", "timestamp", "mesh_tolerance" },
  "groups": [
    { "color": "#RRGGBB",
      "objects": [
        { "id": "几何 hash",
          "quantity": {
            "area": 0,            // 水平投影面积
            "vertical_area": 0,   // 新增
            "mean_height": 0,     // 新增
            "count": 0, "length": 0, "volume": 0
          },
          "mesh": { "vertices": [...], "faces": [...] } }
      ] } ] }
```

**五个关键约定**(沿用决策记录 §十五):

1. **所有量纲全部算出来一起发** —— 构件有四种单位,GH 不知道会用到哪个,索性全算全发
2. **id 用几何 hash** —— 几何不变 id 就不变,增量更新的基础;不能用序号
3. **单位在 GH 端统一转米**
4. **必须有 `origin_offset`** —— 景观模型常带真实地理坐标,three.js 的 float32 在那个量级会抖动撕裂
5. **坐标保持 Rhino 的 Z-up**,由网页端转 three.js 的 Y-up

**出 →** JSON,本地文件 / WebSocket

## L3 — Resolver 解算器(系统的心脏)

**输入**:几何量 + 颜色 + 项目地点
**输出**:一张带来路标签的构件清单

**三条解算规则**:

| 输入 | → | 输出 | 消解掉 |
|---|---|---|---|
| 颜色 | → | 材料族(用户唯一真正的设计决策) | — |
| 竖直面积 ÷ 平面面积 | → | 挡墙用量;并反推 铺装 = 平面 − 墙占地 | 26 条 |
| 项目地点 | → | 气候区 | 48 条 |
| 面法线方向 | → | 墙/台阶/栏杆自动识别 | 11 条 |

凡是没被上面覆盖的子构件,**原样采用 CC 默认值,并打上「假设」标签**。

> 193 条景观配方中,85 条(44%)由几何与地点自动消解;其余 108 条是真正的材料选择。

## L4 — 碳引擎

**一次性碳**

```
碳 = Σ(用量 × 碳因子)
低 / 中 / 高 三档同时算
```

**固碳曲线**(沿用 CC,逻辑斯蒂 S 型):

```
Ct = M / (1 + e^(−r × (t − M/2)))

M = 碳承载力 = 成熟系统总储碳 (TCP)
r = 分布式固碳率,拟合到成熟年份
    木本生态系统 80 年 / 草地 20 年
湿地例外 —— 用线性回归
```

**五笔账,按年份排到时间轴上累加**:

| # | 科目 | 发生时点 | CC 是否含 |
|---|---|---|---|
| ① | 材料生产 A1-A3 + 运输 A4 + 施工 A5 | 第 0 年 | ✅ |
| ② | 现状损失(砍树、土壤扰动) | 第 0 年 | ✅ |
| ③ | 维护 B2-B3 | 周期性 | ❌ **不含**(见 §七) |
| ③ | 更换 B5 | 按寿命脉冲 | ✅ |
| ④ | 植物 + 土壤固碳(非线性) | 每年 | ✅ |
| ⑤ | 期末处置 C | 期末 | ❌ 不含 |

**研究周期 60 年**(跟随 CC V2 —— 他们的固碳数值就是投影到第 60 年算出的,用他们的数据必须对齐)。

**同时算两条曲线**:设计方案 + "什么都不做"基准。两线之间的面积,就是这个设计的真实代价或贡献。

**出 →** 逐年时间序列 + 累计净碳曲线 + 碳中和年

## L5 — 表现层

详细规格见 `Carbon工具-UI交互设计.md`。要点:

- three.js 视口按颜色着色(与 Rhino 视口同一套色)
- 主图是**双曲线对比**
- 每个数字旁边显示**来路**,点开能看到"这 12 吨来自你画的 30 米挡墙"
- **区间上下限不是误差棒,是设计选择空间** —— 下限 = 全部选低碳做法能到的水平。所以它是个可执行目标,不是免责声明

## L6 — 后端

```
几何(大、敏感、对比时不需要)        →  只在本地,从不上传
方案快照(映射+量+碳结果+缩略图)     →  上云,几十 KB
材料库(只读公共数据)                →  静态 JSON,不进数据库
```

三个好处:**隐私**(很多事务所禁止上传模型)、**成本**(免费档数据库能装几千用户)、**离线可用**(不登录也能完整使用)。

代价:重开半年前的旧方案看不到三维,只有数据、图表和缩略图。可接受。

后端要设计成**可自建、可替换**。

## AI 层(横切,不占一层)

Tool calling 只操作「假设」槽位。典型情景:

- "把这块广场的铺装换成透水砖会怎样" → 换材料族,重算,给出差额
- "怎么让这个方案 30 年内碳中和" → 在假设槽位上搜索
- "这个数字为什么这么高" → 沿来路链条回溯

# 第四部分:用户流程

对比:CC 要用户在网页上重画一遍多边形,再从 193 个复合场景里挑一个。

1. **在 Rhino 里选一个颜色,把几何塞进 CC_Group 电池**
   颜色即材料族。同一套色贯穿 Rhino 视口 → 网页三维 → 图例 → 图表 → 报告,视觉语言由用户自己定义。

2. **打开 Sync,浏览器里出现三维模型和第一版碳结果**
   此刻所有几何相关项已是实测,其余为 CC 默认假设。结果立刻可用,不需要先填一堆表。

3. **在网页上填一次项目地点**
   气候区就此确定,48 条生态配方自动定档,以后不再问。

4. **顺着「假设」标签往下走**
   想更准,就去模型里把灯、排水、树画出来;或者直接在网页上改那个假设值。

**用户从头到尾没有选过一次"场景"。**

原计划"做 20 个场景入口盖住 80%"因此取消 —— 那是在压缩一个本来就不该由用户逐条挑选的列表,而且是拿精度换易用性。这里两样都拿到了。

# 第五部分:另外两个待定项的结论

## 六、单株乔木 —— 做,而且很便宜

决策记录原文说"CC 是**有意**按面积而非茎密度计量的"。**数据显示并非如此。**

CC 的城市树固碳本身就是按**株距**参数化的,只是被冻结成了三个点:

| 树冠覆盖 | 株距 | ㎡/株 | 固碳 kgCO₂e/㎡ | 反解:每株 |
|---|---:|---:|---:|---:|
| 17% | 12 m | 144 | −2.66 | −383 |
| 35% | 6 m | 36 | −5.63 | −203 |
| 50% | 4 m | 16 | −8.51 | −136 |

街道树配方里的构件名更直白:

```
5 cm Cal. B&B/Box Tree Planting (1 Tree/10 SM)
```

**每 10㎡ 一棵,写死的。**

Rhino 里树本来就是点或块,棵数、位置、间距全都现成。三点插值即可,工作量极小。

> ⚠️ **每株固碳随密度下降**(竞争)。绝不能写成 `N × 常数`,必须沿这条曲线插值。
> 这也是讲故事的素材:"多种一倍的树,固碳不到一倍。"

## 七、维护碳 —— 一期不做,但理由要换

搜遍 259 条构件:维护/运营碳**一条都没有**。命中的 10 条全是灌溉**硬件**(管道、喷头、控制器、气象站、水泵)的 A1-A3 生产碳,没有一滴水、一次修剪。

**关键推论**:做维护碳 = **离开 CC 数据集**。要自己建因子、自己找文献、自己扛争议 —— 这恰好推翻了"用 CC 数据省 3–5 人年"的核心逻辑。

**建议**:

- 一期不算
- 把灌溉硬件(数据里有)单独显示出来当钩子
- 报告里明写"与 CC 一致,不含 B2–B3 运营碳"
- 列为二期独立模块,有自己的文献支撑

这样方法论边界干净,不会让一个模块拖垮整个数据策略的合法性。

# 第六部分:推进顺序

每一步都要能独立跑通、看得见结果,不要一上来就啃最难的。

1. **先做 L0 的来路标注**
   纯数据工作,不写代码就能开始,而且它定义了后面所有接口的形状。约 25 个类别。

2. **L3 解算器 + L4 碳引擎,纯 Python/JS,喂假数据**
   原型已跑通并与 CC 逐位对上。先把算法钉死,再谈界面和插件。

3. **L1 GH 电池,输出 JSON 到文件**
   先不碰 WebSocket。`CC_Group` 颜色分组 + 竖直/水平面积拆分。.gha 必须本地编译。

4. **L5 网页骨架:three.js 读 JSON,着色,侧栏列表**
   此时已是一个能用的完整闭环,只是靠手动传文件。

5. **把传输层换成 WebSocket**
   协议不变,网页只改数据源那一个函数。风险被隔离在最后。

6. **L6 后端、AI 层、报告导出**
   都是在已经跑通的闭环上做加法,可以并行。
