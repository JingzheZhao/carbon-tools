## 2. The CC Group component

Files: [Components/CCGroupComponent.cs](../src/Sitewise/Components/CCGroupComponent.cs),
[Components/CCGroupComponentAttributes.cs](../src/Sitewise/Components/CCGroupComponentAttributes.cs)

### 2.1 Basic shape

- Input: `Geometry` (list, accepts any geometry)
- Output: `Tagged Objects` (list)
- **No separate Colour input** — colour is chosen entirely through the swatch on
  the component body and does not exist as a wireable parameter. Treating colour
  as an ordinary input was considered and explicitly rejected: the swatch already
  picks a colour, so an extra input port would be duplication.

### 2.2 Colour picking (three iterations)

1. **First version**: a native `Param_Colour` added via
   `pManager.AddColourParameter`, with colour chosen through the right-click "Set
   Colour…" menu. It worked, but users could not tell it was clickable and found
   needing a right-click unintuitive.
2. **Second version**: a custom `CCGroupComponentAttributes : GH_ComponentAttributes`
   drawing a permanent swatch beneath the component body. A **single click** (no
   right-click) opens `Rhino.UI.Dialogs.ShowColorDialog` — Rhino's own colour
   wheel and RGBA panel, the same dialog the right-click menu invokes. The swatch
   shows the current colour live, and the label switches between black and white
   according to background brightness so it stays readable.
3. **Third version**: the colour input port was removed entirely (see 2.1) and
   colour became persistent component state:
   - a `CurrentColor` property on the component instance
   - `Write` / `Read` overridden (`GH_IO.Serialization.GH_IWriter/IReader`, using
     `SetDrawingColor` / `GetDrawingColor`) so the colour is written into the
     `.gh` file and survives save and reopen

### 2.3 Icon

- Initially `Icon => null`, which makes Grasshopper substitute a checkerboard
  "missing icon" placeholder. Feedback was that it duplicated the swatch and added
  nothing.
- Replaced with a 24×24 filled orange dot generated at runtime with
  `System.Drawing.Graphics` — a clean substitute for the default placeholder.

### 2.4 Output data structure: `TaggedGeometry`

File: [Components/TaggedGeometry.cs](../src/Sitewise/Components/TaggedGeometry.cs)

- A plain data class: `{ IGH_GeometricGoo Geometry, Color Color }`
- Passed downstream wrapped in Grasshopper's built-in `GH_ObjectWrapper` rather
  than **implementing our own `IGH_Goo`** — that would drag in `CastFrom`,
  `CastTo`, `Write`, `Read` and a pile of other boilerplate, and
  `GH_ObjectWrapper` is exactly the official shell Grasshopper provides for
  carrying an arbitrary .NET object through a generic parameter.
- This is the architecturally important step of the session. Previously colour
  existed only inside the CC Group component (the `CurrentColor` field) and **did
  not travel down the wire**. Now colour is packed alongside each geometry object,
  which is the only way CC Sync can know which colour group each object belongs to.

### 2.5 Viewport preview colouring

- `DrawViewportWires` / `DrawViewportMeshes` overridden, replacing the default
  implementation so Grasshopper's green/selection preview colours are no longer
  used
- Iterates the output parameter's `VolatileData.AllData(true)`, unwraps each
  `TaggedGeometry`, and uses `tagged.Color` to build `GH_PreviewWireArgs` and a
  `DisplayMaterial` for wireframes and meshes respectively
- Result: what you see in the Rhino viewport is the colour the user picked on the
  swatch, not Grasshopper's default palette

## 3. The CC Sync component

File: [Components/CCSyncComponent.cs](../src/Sitewise/Components/CCSyncComponent.cs)

### 3.1 Component shape (matching the sketch in decision record §14)

Inputs:

- `Objects` (generic, list) — takes the `Tagged Objects` output of one or more CC
  Group components. Grasshopper natively merges multiple wires into one input as a
  single list, so a manual "+" port (`IGH_VariableParameterComponent`) has **not**
  been built; the native behaviour is enough for now.
- `Run` (Boolean) — the continuous sync switch. True starts the local server and
  refreshes the data on every recompute; false shuts the server down.
- `Open` (Boolean) — button semantics, with **rising-edge detection** (the
  `_previousOpen` field), so the browser opens only on the false→true transition.
  Without this, dragging a slider would spawn a stack of tabs. The decision record
  singles this out as the reason the sync switch must be split into two inputs.

Outputs:

- `Status` (text): a description of the current state, e.g.
  `Running on http://localhost:53665/ - 12 objects across 3 groups`
- `Port` (integer): the local server port, `-1` when not running

`RemovedFromDocument` shuts the server down, so deleting the component does not
leave a thread and a port hanging.

### 3.2 The sync protocol JSON (decision record §15)

File: [Sync/SyncJsonBuilder.cs](../src/Sitewise/Sync/SyncJsonBuilder.cs)

```json
{
  "meta": {
    "units": "m",
    "origin_offset": [x, y, z],
    "timestamp": "2026-08-26T12:00:00Z",
    "mesh_tolerance": 0.01
  },
  "groups": [
    { "color": "#E67E22", "objects": [ { "id": "...", "quantity": {...}, "mesh": {...} } ] }
  ]
}
```

- Grouped by `TaggedGeometry.Color`, converted to `#RRGGBB` hex
- **Unit conversion to metres**: reads `RhinoDoc.ActiveDoc.ModelUnitSystem`,
  computes a factor with `RhinoMath.UnitScale(...)`, and multiplies every length,
  area, volume, and mesh coordinate by it. The web side never has to care whether
  the Rhino document is in millimetres or feet.
- **origin_offset zeroing**: takes the union bounding box of all incoming
  geometry and uses its `Min` point as an offset, subtracting it from every mesh
  coordinate. This avoids real-world survey coordinates — often in the hundreds of
  thousands — reaching three.js, where float32 precision would cause jitter and
  tearing. The decision record §15 names this trap explicitly.
- **mesh_tolerance**: read from `RhinoDoc.ActiveDoc.ModelAbsoluteTolerance`

### 3.3 Quantities and meshes per object

Files: [Sync/GeometryQuantities.cs](../src/Sitewise/Sync/GeometryQuantities.cs),
[Sync/MeshExport.cs](../src/Sitewise/Sync/MeshExport.cs)

- `Point` → `count = 1`
- `Curve` → `length` (`GetLength()`)
- `Brep` / `Mesh` → `area` (`AreaMassProperties`), plus `volume`
  (`VolumeMassProperties`) when closed
- `Surface` / `Extrusion` → converted to `Brep` and handled by the logic above.
  **A trap here**: in RhinoCommon `Extrusion` derives from `Surface`, so a
  `switch` with `case Surface` before `case Extrusion` makes the compiler declare
  the latter unreachable and raise `CS8120`. Two switch branches had to be
  reordered before it compiled.
- **Geometry id**: not an exact per-vertex hash but a "shape signature" proxy —
  type name, bounding box, and either mesh vertex/face counts or curve length,
  concatenated into a string, MD5'd, and truncated to 16 characters. Adequate as a
  candidate key for incremental updates, but not a strict uniqueness guarantee,
  and recorded as a known simplification.
- **Mesh export**: `Brep` / `Surface` / `Extrusion` are meshed with
  `Mesh.CreateFromBrep(..., MeshingParameters.Default)` and `Append`ed together;
  a `Mesh` is used directly. Coordinates are scaled by `unitScale` and then have
  `origin_offset` subtracted. Faces are emitted as they are, `[a,b,c]` for
  triangles or `[a,b,c,d]` for quads.

### 3.4 The embedded local server

File: [Sync/SyncServer.cs](../src/Sitewise/Sync/SyncServer.cs)

Implements decision record §16 — a local server inside the Grasshopper component
rather than Speckle:

- Uses `System.Net.HttpListener` bound to `http://localhost:{port}/`. Binding to
  `localhost` rather than a wildcard means no administrator rights or URL ACL are
  needed on Windows.
- **Finds a free port automatically**: starts a `TcpListener(IPAddress.Loopback, 0)`
  to let the OS allocate a port, reads the number, stops the listener immediately,
  and hands that port to `HttpListener`.
- A background `Thread` (`IsBackground = true`) runs a blocking
  `listener.GetContext()` loop. No callbacks, so the logic stays simple and hard
  to race.
- Routes:
  - `GET /data.json` → the current sync JSON, refreshed by `UpdateData()` which CC
    Sync calls from every `SolveInstance`
  - `GET /` (and every other path) → the 3D preview page (next section), packed
    into the `.gha` as an **embedded resource**, so the plugin depends on no
    external file path and is fully self-contained

## 4. The web 3D skeleton (three.js)

File: [WebAssets/viewer.html](../src/Sitewise/WebAssets/viewer.html)

This is step 3 of the sequence in decision record §16 ("web skeleton: three.js
reads the JSON, displays in 3D, colours by group, lists groups in a sidebar").
Going straight to WebSocket was proposed during the session; the document's advice
not to tackle WebSocket first won out, on the grounds that the full chain
(Grasshopper → local server → web 3D) should be proven before the transport layer
is replaced.

### 4.1 Technology choices

- three.js r128 from a CDN (`cdn.jsdelivr.net`) with the non-module build of
  `OrbitControls.js`, avoiding the extra complexity of the ES Module version in
  this setting
- Packaging: the whole `viewer.html` is an `<EmbeddedResource>` in
  `Sitewise.csproj`, and `SyncServer` reads it back with
  `Assembly.GetManifestResourceStream("Sitewise.WebAssets.viewer.html")` and
  returns it as a string

### 4.2 Coordinate conversion (decision record §15, item 5)

Rhino is Z-up right-handed; three.js is Y-up right-handed. The conversion is:

```js
threeX = rhinoX
threeY = rhinoZ
threeZ = -rhinoY
```

This swaps the axes **while preserving right-handed chirality**. Simply exchanging
Y and Z would turn a right-handed system into a left-handed one, flipping triangle
winding order and breaking backface culling.

### 4.3 Page structure

- Left viewport: `PerspectiveCamera`, `WebGLRenderer`, `OrbitControls`, ambient
  plus directional light, and a `GridHelper` ground plane
- Right sidebar: an "N objects, M groups" summary at the top, then one row per
  colour group (swatch, hex colour, object count, show/hide checkbox)
- Mesh rebuilding: triangles in `obj.mesh.faces` are used directly; quads are
  split into two triangles (`[a,b,c]` + `[a,c,d]`). Geometry is built with
  `THREE.BufferGeometry` and `Float32BufferAttribute`, and each group gets a
  single `MeshStandardMaterial` in its colour.
- **Polling refresh**: every 1.5 seconds, `fetch('/data.json', {cache:'no-store'})`
  re-reads the data and rebuilds the entire scene. This is brute-force full
  rebuild rather than incremental update — the interim approach under the decision
  to prove the chain with HTTP polling first and swap in WebSocket later.
- On first load the camera is aimed at the scene's bounding box automatically
  (`Box3.setFromObject` plus a simple distance and position calculation)

### 4.4 How it was verified

Rhino was not opened. Instead the compiled `.gha` was copied to a `.dll`
extension and the `SyncServer` class loaded directly with PowerShell
`Add-Type` — the class depends on no RhinoCommon or Grasshopper types, so it runs
standalone. Two hand-written sample JSON groups were fed in (a rectangular
surface and a cube), the server started, and:

- `curl` (`Invoke-WebRequest`) confirmed `/data.json` and `/` both returned 200
- Claude Code's browser tool opened the page, and `get_page_text` and
  `read_console_messages` confirmed:
  - the sidebar showed "2 objects, 2 groups"
  - both colour groups (`#E67E22`, `#3498DB`) were listed correctly
  - the console was clean — three.js and OrbitControls loading, `fetch`, and scene
    construction all raised nothing

## 5. Known simplifications and open items

- **The Objects input has no manual "+" port**
  (`IGH_VariableParameterComponent`). It relies on Grasshopper's native wire
  merging, which is sufficient but less explicit than the sketch in the document.
- **The geometry id is a shape signature, not a strict content hash**, and it is
  not yet used for real incremental updates. Every sync rebuilds the JSON in full
  and the web side rebuilds the whole three.js scene.
- **The web side polls `/data.json` every 1.5 seconds rather than receiving
  pushes.** Replacing the transport with WebSocket was the last thing discussed
  and has not been started. The decision record is clear that the protocol does
  not change: the web side swaps out the one function that pulls data, and the
  Grasshopper side changes from answering HTTP requests to pushing.
- **Curves and points are not drawn in the 3D view.** Their `mesh` field is
  `null` in the protocol and they carry only `length` or `count`. `viewer.html`
  currently draws only objects that have a mesh, and whether curves should appear
  on the web has not been decided.
- **`_statusLine` is stored but unused.** It is reserved in `SyncServer`;
  the `/` page does not yet display server-side status text, so it is a
  placeholder.
